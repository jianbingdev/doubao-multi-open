# 发一个新版本（完整流程）

适用场景：代码改完了，要让所有用户都能收到更新。

---

## 最快的方式：一条命令

```bat
cd /d D:\豆包多开开发\doubao-multi-open-3.0.13
set GH_TOKEN=ghp_你的token
node _release\release.js 4.1
```

第一次跑会提示你写更新说明（见下面第 1 步）。写好后再跑一次，全流程自动完成。

---

## 分步说明

### 0. 先把代码改完并自测

发版脚本**不包含任何测试**，它只负责打包和上传。改动必须自己先 `npm start` 跑通。

### 1. 写更新说明

第一次执行某个版本号时，脚本会生成模板并停下：

```
已生成更新说明模板: _release\notes\v4.1.md
```

打开填内容，`## 本次更新` 下面的条目会原样出现在：
- 软件里「检查更新」弹窗的更新说明区
- GitHub Release 的正文

```markdown
## 本次更新

- 新增 xxx 功能
- 修复 xxx 在 xxx 情况下失效的问题

## 功能一览

多账号视图池 · 在线状态检测 · 套餐识别 · 跨账号完成提醒 · 视频生成后台等待 · 自动更新
```

临时想直接给文本也行：`node _release\release.js 4.1 --notes "- 改了什么"`

### 2. 先试运行一次（不上传）

```bat
node _release\release.js 4.1 --dry-run
```

它只做本地动作：改版本号 → 构建便携版 → 压缩成 zip，不碰 GitHub。

跑完检查三件事：

- `_release\dist\DoubaoMultiOpen-v4.1-core.zip` 生成了，约 300 KB —— 这是自动更新真正下的包
- `_release\dist\DoubaoMultiOpen-v4.1-windows-portable.zip` 生成了，约 143 MB —— 只给首次安装的人
- `_release\build\v4.1\resources\app\package.json` 里的 `version` 是 `4.1`

想更稳妥可以让它直接跑一遍：双击 `_release\build\v4.1\启动豆包多开.bat`，看侧栏徽标是不是 `v4.1`。

> `--dry-run` 会把本地 `package.json` 改成新版本号。不想留着就手动改回去。

### 3. 正式发布

```bat
set GH_TOKEN=ghp_你的token
node _release\release.js 4.1
```

两个参数可以复用中间产物，省时间：

| 参数 | 作用 |
|---|---|
| `--skip-build` | 复用 `_release\build\v<版本>` 已构建好的目录（dry-run 刚跑过就能用） |
| `--skip-source` | 只发 Release，不推源码到 main |

### 4. 验证

脚本最后会打印 `releases/latest` 的实际结果。正常长这样：

```
[7] releases/latest => v4.1  DoubaoMultiOpen-v4.1-windows-portable.zip
```

再自己确认一遍客户端侧：打开旧版 → 点侧栏版本徽标 → 应该显示「最新版本 v4.1」+ 更新说明 + 「立即更新」按钮。

## Token 怎么来

发布需要 GitHub 写权限，用 Personal Access Token：

1. https://github.com/settings/tokens → **Generate new token (classic)**
2. 权限只勾 **`repo`**
3. 复制 `ghp_...`

脚本只从环境变量 `GH_TOKEN` 读取，不写进任何文件。用完建议立刻 Revoke。

---

## 脚本到底做了什么

| 步骤 | 动作 | 失败会怎样 |
|---|---|---|
| 0 | 校验版本号必须大于当前版本 | 直接退出，不做任何改动 |
| 1 | 改 `package.json`（1 处）和 `package-lock.json`（2 处） | 写完立刻校验 JSON 可解析、依赖条目数不变 |
| 2 | 复制 Electron 运行时 + 组装 `resources\app` | 缺文件就报出具体文件名 |
| 3 | 用 PowerShell `Compress-Archive` 打包，并校验 ZIP 头 | 产物不是有效 ZIP 就删掉报错 |
| 4 | 8 个源文件推到 `main`（单个 commit，原子） | 推失败则整个流程停止 |
| 5 | 建 tag `v<版本>` + Release（tag 指向刚才那个 commit） | 已存在则复用并覆盖说明 |
| 6 | 上传 zip 为 Release 资产，同名旧资产先删 | 上传失败直接报 HTTP 码 |
| 7 | 核对 `releases/latest` | —— |

**关于第 4、5 步的顺序**：先推源码、再建 Release，tag 会自动落在最新 commit 上。上一版（v4.0）出过问题——先建 Release 后推源码，结果 tag 指在旧提交，GitHub 自动生成的源码包还是旧版本。

## 版本号规则

- 客户端只认**远端 > 本地**才提示更新，所以版本号必须递增。脚本会拦截低版本号。
- 只比较前三段数字，`v` 前缀忽略：`4.0`、`4.0.0`、`v4.1` 都合法。
- `manifest` 里的版本号来自 **tag 名**（去掉 `v`），不是 `package.json`。所以 tag 必须和版本号一致——脚本已经保证这一点。

## 三个必须知道的坑

### 1. 每次更新，用户要下 143 MB

Release 里只有一个完整包，客户端「检查更新」会自动选中它。这是完整包换来的代价：更新后目录结构永远一致，不会缺 DLL。

想瘦身的话，可以额外传一个增量包（只含 js/html），但要注意 `main.js` 的 `normalizeManifest` 取的是 **assets 里第一个 `.zip`**，顺序取决于上传顺序。要做得先改这段逻辑。

### 2. 别在源码目录里点「检查更新」

从源码目录（`npm start`）运行时，更新的目标目录是源码目录本身。完整包解压后会把 `DoubaoMultiOpen.exe`、一堆 DLL 铺进源码文件夹，目录就乱了。

只有便携版的目录结构才适合走自动更新。

### 3. 浏览器说"检测到病毒"是误报

zip 里的 exe 是改名的 `electron.exe`，235 MB、未签名、零下载量，浏览器 Safe Browsing 会判为无信誉。用户在下载列表点「保留」即可。彻底解决只能买代码签名证书。

## 回滚一个已发布的版本

**让用户看不到**：GitHub → Releases → 该 Release → Edit → 勾 **Set as a pre-release** 或 **Save as draft**。`releases/latest` 会跳到上一个正式版，客户端就不会再提示这个版本。

**彻底删掉**：Delete release（tag 可保留可删）。

**只改 tag 指向**：如果源码包内容不对，可以直接 PATCH `/git/refs/tags/v<版本>` 强制指向正确 commit，不用重发。

## 目录说明

```
_release\
  release.js                    发版脚本（唯一入口）
  notes\v<版本>.md              更新说明，逐版本保留
  build\v<版本>\                构建中间产物（357 MB，可随时删）
  dist\DoubaoMultiOpen-v<版本>-windows-portable.zip
  doubao-multi-open-v4.0\       v4.0 手工构建的便携版，留作参考
```

`build\` 可以随时清空，下次发版会重建。`dist\` 每次只保留当前要发的那个包，旧的会被自动删掉。

## 不想用 GitHub 也能更新

软件支持自建更新源：侧栏徽标 → 检查更新 → 左下角「更新源」，填一个 `version.json` 地址即可。

```json
{
  "version": "4.1",
  "url": "https://你的域名/app-4.1.zip",
  "size": 14680064,
  "notes": "- 本次更新内容\n- 第二条",
  "sha256": "可选，填了就校验"
}
```

`url` 指向的 zip 只需要包含程序文件（js/html/package.json），不需要 Electron 运行时——更新只覆盖程序文件，运行时保持不动。
